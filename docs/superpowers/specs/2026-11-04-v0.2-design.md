# Redlines v0.2: a very basic editor worth demoing

*Design, Nov 4, 2026, revised Nov 5 after Stephan's review. It builds on [design.md](../../design.md) and [format.md](../../format.md), and says where it departs from them.*

## Why

v0.1 proved the format and the tracked-change loop, and it ships: a signed, notarized Mac app that installs itself and updates itself. But it isn't an editor yet. There is no Bold in any menu, no find, and no Preferences window. And the one moment that makes the case for a shared format, a person and an agent working in the same document, can't be shown from inside the app.

v0.2 closes those gaps, and only those. It keeps the look v0.1 has: almost no chrome, quiet grays, one red, and thin borders. The bar for adding anything is "would a writer notice its absence in the first ten minutes?"

## The demo

The audience is someone building products at OpenAI or Anthropic. v0.2 is done when this run works on the presenter's Mac, from an installed release build, start to finish, twice in a row:

1. **The website** (redlines.md) argues that humans and AI need a shared document format.
2. **Open a design doc in a code repo.** It renders beautifully: headings, tables, code with quiet syntax colors, images. They should be able to picture it as a pane in Claude or Codex.
3. **Edit and comment.** Turn on Track Changes, make an edit, leave a comment. Bold something from the keyboard.
4. **Ask an agent.** Write "@Claude does the importer handle CRLF? If not, fix this section." A status line shows what Claude is doing ("Searching the importer", "Editing §3"). Then a reply of a few words appears in the thread ("CRLF handled in importer.ts:42. Fixed §3."), and a tracked change in Claude's color appears in the doc. Click `importer.ts:42` in the reply, and that file opens at that line. Accept the change. Then do the same with @Codex.

Claude is the must. If Codex's command line blocks this by the end of the week, v0.2 ships with Claude alone and Codex follows, since the interface doesn't change.

## Goals

1. **Basic editing:** formatting from menus and shortcuts, find and replace, opening recent files, printing, pinch to zoom, a basic file sidebar, and never losing work.
2. **A Preferences window** with four small panes.
3. **Rendering good enough to sell the pane:** syntax-highlighted code, images, task lists.
4. **Agents in comments:** @Claude and @Codex, behind an interface generic enough for an OpenClaw agent or a local model.
5. **Nothing to install but the app:** the `redlines` command line ships inside the app as a native program. Redlines never needs Node on the person's computer.
6. **A disciplined split** between the core and plugins, and between what the desktop app and an embedded pane each carry.

**Stretch goals, if time remains at the end of the week, in this order:** the Google Docs copy and paste round trip ([#31](https://github.com/skadauke/redlines/issues/31)), then the Agent Client Protocol provider (see Routes to the agents).

## One rule for all of this

**What the document shows is in the file.** Format §1.1 promises no sidecar files and no database. v0.2 reads that strictly: if something stays on screen in or beside the document, it is in the `.md`, and everyone who opens the file sees it. If it isn't in the file, it doesn't show in the document.

The app may keep things of its own, such as settings and logs. They are the app's: they don't sit next to the document, the document never refers to them, and deleting them changes nothing about any document.

There is one exception, on purpose: a run's live line in the thread, which holds its status, the first-run question and any failure. It is about right now, like a cursor or a progress spinner. It is never written to the file, and it doesn't survive closing the document.

## Non-goals

- Word import and export ([#32](https://github.com/skadauke/redlines/issues/32)). It's important, and it comes next, in v0.3.
- A working embedded pane. v0.2 only keeps the door open and proves it with a smoke test.
- MCP servers and other outside tools for agents. The design leaves room for them (the third scope level below), but v0.2 doesn't turn them on.
- The chat panel (design §8.5), agent levels (§8.2), animated agent edits (§8.4), and a command palette (§5.9).
- A viewer for agent logs. They are plain files, for troubleshooting.
- Sign in with ChatGPT, API key entry, and any agent loop of our own (design §8.6 keeps them for later).
- A public plugin API and worker isolation for plugins. The API stays internal and may change.
- Agents on Windows and Linux. The code should not preclude them, but only the Mac is tested.

## Anti-goals

These would make v0.2 a failure even if everything technically works:

- **An agent writing walls of text** in a comment thread.
- **New chrome:** toolbars, formatting buttons, status bars, badges, or a settings sidebar with dozens of options.
- **An untracked agent edit,** or an agent that writes anything but this document.
- **An agent started by someone else's words.** A comment already in a file, from a colleague or an attacker, must never start a run.
- **Redlines touching Claude or ChatGPT credentials.**
- **Something in the document that isn't in the file,** apart from a run's live line.
- **A harness of our own.** Claude Code and Codex already run the agent loop, the tools and the sign-in. Redlines starts them and reads what they say.
- **Needing Node,** or any other runtime, on the person's computer.

## Decided by Stephan

- Formatting has menu items and shortcuts, with no buttons.
- The demo is a design doc, a question that needs the folder, and a tracked edit.
- An agent answers in the thread, and makes tracked edits when asked.
- Agents write the way people write comments: extremely concise, often not complete sentences.
- While it works, an agent shows very short status lines that it writes itself, saying what's actually happening right now.
- Agents live in plugin land, behind a generic interface. Claude and Codex come first.
- An embedded pane may carry plugins too, but probably different ones from the desktop app.
- Copy and paste is a stretch goal; Word comes after v0.2.
- No sidecars is a rule of Redlines. Showing something in the document that isn't in the file is the worry. (The rule's wording above is mine.)
- A log of agent communication exists, for troubleshooting.
- Redlines doesn't depend on Node on the host computer.
- Claude goes through `claude -p`, so people can use their subscriptions. Support the most popular supported routes to the agents, and don't reinvent the harness.
- A two-finger trackpad gesture zooms in and out.
- A very basic file library in the left sidebar, so the presenter can look at the files an agent refers to.
- The @ picker also lists the other collaborators in the document's ledger.
- The Preferences panes are right in outline. The Agents pane may change with the agent work.

Everything else below is my call. Disagree freely.

## Editor basics

### Menus

Standard macOS items (Undo, Services, Emoji & Symbols, and so on) stay as they are. This is what v0.2 adds.

| Menu | Items, with shortcuts |
| ---- | --------------------- |
| **File** | New ⌘N, Open… ⌘O, **Open Recent**, Save ⌘S, Save As… ⇧⌘S, **Rename…**, **Reveal in Finder**, Close ⌘W, **Print…** ⌘P |
| **Edit** | **Paste as Plain Text** ⇧⌘V; **Find**: Find ⌘F, Find Next ⌘G, Find Previous ⇧⌘G, Find and Replace ⌥⌘F, Use Selection for Find ⌘E |
| **Format** (new) | **Bold** ⌘B, **Italic** ⌘I, **Inline Code** ⌃\`, **Strikethrough** ⌃⇧\`, **Link…** ⌘K, **Clear Formatting** ⌘\\, **Add Comment** ⌥⌘M |
| **Paragraph** (new) | **Body Text** ⌘0, **Heading 1–6** ⌘1–⌘6, **Quote** ⌥⌘Q, **Bulleted List** ⌥⌘U, **Numbered List** ⌥⌘O, **Task List** ⌥⌘X, **Code Block** ⌥⌘C, **Table** ⌥⌘T, **Horizontal Rule**, **Indent** ⌘], **Outdent** ⌘[ |

A menu item shows a check mark when the caret is inside that format. With no selection, an inline format applies to the word under the caret. Hovering the file name in the title bar shows the word count and when it was last saved, so there is no status bar.

**Left out on purpose:** tabs, focus and typewriter modes, a read-only mode for Markdown, a toolbar, an always-on-top window, an outline panel, file search and recent-file lists in the sidebar, file operations in the sidebar, underline (Markdown has none), footnote, math and table-of-contents tools, an image uploader, exports other than printing, Duplicate, Move To and Delete File, custom shortcuts, a language picker, and options for how Markdown is written (Redlines keeps what a file already has, and writes `#` headings, `-` bullets and `1.` numbers).

### Text size and pinch

⌘+, ⌘−, ⇧⌘0 and a two-finger pinch on the trackpad all change one text size, the one in Preferences. A pinch steps through the same ladder as ⌘+ and ⌘− as the fingers move. It doesn't magnify the page, so text stays sharp and re-wraps. The document and its margin notes scale together, and the title bar doesn't. WKWebView reports a pinch as `gesturechange` events; the page must prevent the default so that it doesn't also magnify. Other webviews report Ctrl plus wheel, which is cheap to handle at the same time.

This can only be judged with fingers on a real trackpad, so Stephan tries it before it merges.

### The file sidebar

v0.1 already has a file sidebar (⌃⌘S and the Files icon, hidden by default), and I wrongly listed "a file library" as left out while keeping it. Today it lists only Markdown files, only from the document's own folder, so the file an agent cites often isn't there and couldn't open anyway. v0.2 turns it into the very basic library the demo needs, and nothing more:

- **Root:** the same folder an agent may read (see Scope): the repository root when the document is in a git repository, and otherwise its own folder. It's a convenience, not a fence: the agent may also read what the sidebar hides (see Scope). If that folder is the home folder or the disk's root, the sidebar lists the document's own folder instead. The folders above the open document start expanded.
- **What it lists:** every file and folder, except hidden ones and whatever `.gitignore` ignores, so `node_modules` and build output never appear. A folder is read when it's expanded. Markdown files read as the main thing, and others sit one step grayer. There are no file icons.
- **Opening:** Markdown opens in this window as it does today, and ⌘-click opens a new window. While a run is live in this window, a click opens a new window too (see Pitfalls). Other text files open read-only in Raw, with syntax colors and with no Track Changes or review. Anything else, such as an image or a PDF, opens in its default app.
- **Citations:** in a comment, a path or `path:line` naming a real file inside that folder is a link. Clicking it opens the file in a new window at that line, so the document and the thread stay in view. The link is worked out when the comment is shown. The file holds plain text, and a link only ever opens a file for reading.
- **Staying current:** it refreshes when the window gets focus, as it does today, and when a run ends.

Finding the repository root means walking up to a `.git`, and reading `.gitignore` needs no git either (the Rust `ignore` crate does it), so git needn't be installed.

### Formatting with Track Changes on

Formatting must follow Track Changes like any edit. With tracking off, it goes through `untrackedEdit`, as typing does. With tracking on, it writes `fmt` marks. Format §2.6 already defines the operations v0.2 needs: `+bold`, `-bold` and the same for `italic`, `strike` and `code`; `+link`, `-link=URL`, `link=URL`; `+check`, `-check` for task boxes; and `was=TYPE` for block changes such as a paragraph becoming a heading. v0.1 only parses and keeps those marks, so v0.2 has to implement them in `@redlines/format` and the review plugin: writing them, showing them, and accepting and rejecting them. Where §2.6 is silent, such as overlapping formats, extend it deliberately, in the same PR. This is the riskiest format work in v0.2, and it follows the same rules as the rest: no marker starts a line, and reject restores the exact bytes.

### Never losing work

Asking before quitting with unsaved edits, and New in a new window ([#14](https://github.com/skadauke/redlines/issues/14)), are in.

## Preferences

A small window (about 560×400) of its own, opened with ⌘,. Four panes, reached by icons along the top with hover hints, in the app's grays and thin rules. There is no sidebar and no search. Changes apply at once, and there is no Save button. Plugins contribute their settings through the API, so a pane has only what the installed plugins need. It replaces the theme submenus in the app menu.

| Pane | Settings |
| ---- | -------- |
| **General** | Your name and handle, as they appear on changes. On launch: reopen last document or show a new one. Check for updates automatically. Rotate the Dock icon. Install the `redlines` command line. |
| **Appearance** | Light theme, dark theme. Text size. |
| **Editor** | Spell check. Smart quotes and dashes. Close brackets and Markdown pairs as you type. Track Changes on for new documents. |
| **Agents** | The agents found on this Mac, with their state ("Signed in", "Not found"). What agents may read (see Scope). Show Agent Logs. |

## Rendering

- **Code blocks:** syntax colors drawn from the theme's grays and muted tones, with no background chrome beyond today's. Languages load on demand.
- **Images:** local paths relative to the document, and URLs. A missing image shows its alt text quietly. An image URL inside a pending change isn't fetched until the change is accepted, and shows its alt text until then. Otherwise an agent misled by text it read could leak what it read through the URL the moment its edit lands. Local images load as usual, and the demo doc uses them. Narrowing the file write scope ([#26](https://github.com/skadauke/redlines/issues/26)) must land before images do.
- **Task lists:** real checkboxes. Clicking one is an edit, tracked when Track Changes is on.
- **HTML entities** render ([#12](https://github.com/skadauke/redlines/issues/12)).
- **A long design doc** (at least 5,000 words, 200 marks) stays smooth while typing and scrolling. Measure it; fix what the demo doc shows.

Math and Mermaid keep showing as formatted source.

## Agents

### What happens

1. **The picker.** In a comment or reply, typing `@` opens a small picker. Agents found on this Mac come first, then the people in this document's ledger (its `people`, format §5.3), leaving out you and `unknown`. Your own agent entries, such as `claude-you`, are covered by the agent's row. Someone else's agent, such as `claude-bo`, is listed like a person. Picking one puts a mention in the comment as plain text (`@Claude`, `@bo`). This needs no change to the file format.
2. **Who starts what.** Naming a person starts nothing and sends nothing, because Redlines has no backend. They see it when they open the file. Posting a comment that names an agent starts a run in that thread. **A run starts only from the act of posting in this app's comment box.** The trigger is that action, never text read from the file, so a mention arriving by reload, paste or git never starts anything.
3. **Consent.** The first run of an agent in a folder asks once, on the run's live line: "Let Claude read this folder?", naming the folder. Its contents go to that agent's provider, so this is the person's call. The answer is remembered per agent and folder, in the app's settings, not in the document. "Just this document" runs at the narrower scope.
4. **Status.** While it runs, one quiet gray line sits in the thread: the agent's dot and name, then its current status. It changes in place, with a Stop control on hover.
5. **Result.** The reply and any tracked changes appear, in the agent's color. The person can keep typing throughout (see Where the tools run). If the agent ends without calling `reply`, its final message becomes the reply, cut to fit the limits.
6. **Failure.** If the run fails or is stopped, the live line says so until the person dismisses it or posts again. Nothing about the failure goes in the file. Tracked edits made before it stay, and are reviewed like any others.

An agent is an author that acts for a person, as in §8.1: the handle is `claude-<you>` or `codex-<you>`, the name "Claude" or "Codex", and the ledger entry has `agent: true` and `for: <you>`. Its color comes from its handle, by the rule the editor already has.

Runs hold no state of their own. Each one reads the thread and the document afresh, so all the context a follow-up has is in the file.

### How agents write

The thread reads like people wrote it. "CRLF handled in importer.ts:42. Fixed §3." is the target, and a paragraph is a bug. This is enforced, not just requested:

- **The `reply` tool takes at most 200 characters,** with no blank line. A longer reply fails with an error telling the agent to shorten it, and to put the rest in `details`. Models recover from tool errors, so this is sturdier than a prompt.
- **The longer message is in the file, folded.** `details` (at most 2,000 characters) is written after the reply in the same comment text, separated by a blank line. In the app, the first paragraph of a comment by an `agent: true` author is what shows, and a quiet "More" opens the rest in place. That is everything: no popover, and no second place to look. It needs no format change, because comment text may already hold several paragraphs (format §5.5). Any other tool simply shows it all. Whether it's open is per-person state and is never saved (format §5.6).
- **The prompt sets the voice:** a margin comment, fragments welcome, no preamble, no restating the question, cite `file:line` when it answers from the code.
- **Edits carry short notes,** with the same 200-character limit.

### Status lines

The agent writes these itself, through a `status` tool that takes at most 40 characters: "Searching the importer", "Reading tests", "Editing §3". They replace each other, and they are never written to the file. If the agent goes quiet, the provider fills in from its event stream ("Reading importer.ts", or "Thinking…"). That also covers agents that ignore the tool.

### The log

Every run writes a log, for troubleshooting. It is one JSON Lines file per run in the app's log folder (`~/Library/Logs/md.redlines.editor/agents/`), holding what was started (the agent and its version, the flags, the folder, the thread id), every line of the agent's event stream as it came, every tool call with its result, and how the run ended.

Nothing in the app displays it. Help ▸ Show Agent Logs opens the folder in Finder, and a failed run's notification offers the same. By the rule above it isn't a sidecar: it isn't next to the document, the document doesn't refer to it, and deleting it changes nothing.

Logs quote the document and the repository, so they stay on this Mac, are never sent anywhere, and are deleted after 30 days. They record flags and events, never the environment, so no credential can land in one.

The reasoning trace is here. For more, the agents keep their own transcripts: the log's first lines hold the session id, so `claude --resume <id>` picks up that conversation in a terminal. That costs us nothing to build.

### The toolbox

All agents act on the document through the same small set of MCP tools, and have no other way to change it.

| Tool | Does |
| ---- | ---- |
| `view` | The newest text with numbered lines, as in §8.3. No markers |
| `read_thread` | This thread's comments and replies, labeled as untrusted text except for the person's request ([#19](https://github.com/skadauke/redlines/issues/19)) |
| `str_replace` | `old_str`, `new_str`, optional `note`. Same names and errors as §8.3; writes a tracked change in the agent's name |
| `comment` | `quote`, `text`. A new thread on other text |
| `reply` | `text` (200 characters), optional `details` (2,000) |
| `status` | `text` (40 characters) |

Agents never accept, reject or resolve in v0.2. Every result that holds hidden text is labeled as untrusted (§8.1).

### Where the tools run

**In the app, the app is the only writer.** The tools are TypeScript, in a package the plugin uses (say `packages/agent-tools`), and for a run started in the app they run in the webview against the live editor. The agent reaches them over MCP: its config names `redlines mcp --relay <socket>`, which pipes stdio to the running app over a per-run Unix socket (mode 0600), with no TCP port.

Because only one program ever writes an open document, an agent's edit can't race the person's typing, and there is no merging to get wrong. A file-based alternative would need a three-way merge in the middle of a document and its ledger, whose failure mode is a corrupted file. The relay's failure mode is a tool call that fails out loud. It also means a document with no file yet still works, and status lines reach the thread directly.

**Saving.** Posting a comment that starts a run saves the document, if it has a file. While the document has no unsaved edits, each agent edit saves as it lands, so the file holds what the screen shows, and `git diff` shows Claude's change the moment it appears. If the person has typed since, agent edits join their unsaved work, and ⌘S saves both.

### The `redlines` program

Today the command line is TypeScript that Node runs from a repo checkout, so nobody with the released app has it. Design §6.3 promised "a self-contained executable", and v0.2 delivers it: `Redlines.app/Contents/MacOS/redlines`, a small Rust program that embeds the QuickJS engine and the same bundled TypeScript (`packages/cli`'s commands and `@redlines/format`). No format logic is rewritten, so there is still one implementation of the format.

I tested this on Nov 5 with a throwaway on this Mac, running the real `str-replace` and `view` on `docs/design.md`:

| | Measured (arm64, release build) |
| - | - |
| Program size | 1.16 MB, against 0.3 MB for a bare Rust program (so 2.3 MB in a universal app) |
| Startup, with the library loaded | 11–15 ms |
| `view`, 68 KB document | 5 ms; about 30 ms with 77 marks in it |
| `str-replace`, 68–74 KB document | Median 114–131 ms, at most 202 ms |

The speed is about 15 times slower than Node, and it doesn't matter next to a model's turn of several seconds. Node's parser read QuickJS's output fine. The only thing missing was `crypto.getRandomValues`, which the Rust side supplies from the operating system. Bundling Node, Bun or Deno instead would add 60–100 MB per architecture to a 15 MB app.

It does two things:

- **`redlines view|str-replace|comment|reply|accept|reject <file>`** act on the file on disk, exactly as today. This is how agents outside the app work, such as a Claude Code session in a terminal. The app reloads, or shows v0.1's "changed on disk" notice if the person has unsaved edits. `redlines convert` ([#32](https://github.com/skadauke/redlines/issues/32)) lands here later.
- **`redlines mcp --relay <socket>`** is the pipe above. It needs no JavaScript.

Preferences ▸ General installs it by linking `~/.local/bin/redlines` to the app's copy, which needs no password, and says so if that folder isn't on the PATH. `pnpm -s redlines` stays for development, and the Claude Code skill (`integrations/claude-code/SKILL.md`) moves to plain `redlines`.

### Scope

What an agent may read is a setting with three levels. Writing is always this document, through the toolbox, as tracked changes.

| Level | Agent may read | v0.2 |
| ----- | -------------- | ---- |
| **This document** | The document, through the toolbox | Yes |
| **This folder** | Also the files in the document's folder or repo, read-only | Yes, the default |
| **Everything it's set up for** | Also the project's MCP servers and other tools | Later |

"The folder" means the repository root when the document is inside a git repository, and otherwise the document's own folder. If that is the home folder or the disk's root, the run falls back to This document and says so on the live line.

At This folder, the agent may read everything under that folder, including hidden and ignored files such as a `.env`, as it could if the person ran it there themselves. That's why the question names the folder.

**A level has to be what the agent really does, not what we asked for.** Claude can be held to it: with `--permission-mode dontAsk`, reads inside the working folder run and reads outside it are denied, as long as a bare `Read` isn't on the allowed list, and This document passes no read tools at all. Codex is less clear. Its read-only sandbox blocks writes and the network, but it can run read-only shell commands, and I found no way in `exec`'s docs to limit reads to one folder (app-server's sandbox policy mentions read roots, and config mentions permission profiles). The spike finds out. If Codex can't be limited, it still runs, because the demo doesn't depend on the limit, but its question says what's true ("Let Codex read files on this Mac?"), and it offers no "Just this document".

Scope is plain data passed to the provider, so a new level is a new value, not a redesign.

### The agent interface

Providers are plugins. The core and the review plugin know only this shape (a sketch; the builder may refine it):

```ts
interface AgentProvider {
  id: string;                         // 'claude', 'codex'
  name: string;                       // 'Claude', shown in the thread
  detect(): Promise<AgentState>;      // found, signed in, or why not
  run(request: AgentRequest, tools: McpEndpoint, signal: AbortSignal): AsyncIterable<AgentEvent>;
}

interface AgentRequest {
  prompt: string;       // the person's words
  thread: string;
  documentPath?: string;
  folder?: string;
  scope: 'document' | 'folder' | 'everything';
  author: { handle: string; name: string; for: string };
}

type AgentEvent =
  | { type: 'status'; text: string }  // from its event stream; the status tool goes directly to the thread
  | { type: 'done' }
  | { type: 'error'; message: string };
```

`McpEndpoint` is the command to start, such as `redlines mcp --relay <socket>`. `HostAgents` in `@redlines/plugin-api` changes to match: the current one-shot `ask` can't stream. The Mac app adds a small `processes` capability for providers that start programs. It writes every line a program prints to the run's log, so a provider never has to think about logging, and its Rust side starts only the agents that detection found. An embedded host skips providers altogether and supplies `HostAgents` itself, with its own tools.

### Routes to the agents

Redlines doesn't build a harness. Claude Code and Codex already are harnesses, with the agent loop, the tools, the sign-in and the model choice. A provider starts one, hands it the toolbox over MCP, and turns its JSON Lines into status lines. That's on the order of a hundred lines per agent.

| Backend | Route | Whose sign-in | v0.2 |
| ------- | ----- | ------------- | ---- |
| **Claude** | The person's own `claude -p` | Claude Code's: subscription or API key, as they set it up | Yes |
| **ChatGPT** | The person's own `codex exec` | Codex's: ChatGPT plan or API key, as they set it up | Yes |
| **ChatGPT, no terminal** | Sign in with ChatGPT inside Redlines | Redlines would hold tokens and need an agent loop, or would drive `codex app-server` | Later, for writers with a plan and no command line |
| **OpenClaw, Gemini CLI, GitHub Copilot, Cursor, OpenCode, Goose and about 40 more** | One Agent Client Protocol provider (`plugins/agent-acp`), given a command such as `openclaw acp` | Each agent's own | Stretch, then later |
| **Local models** | An ACP agent that supports them (Goose or OpenCode with Ollama), or `codex --oss` | None | Same provider |

**What the research found** (checked Nov 5, 2026; sources at the end; these terms changed several times this year, so re-read them before release):

- **Claude: subscriptions really do need `claude`.** Anthropic doesn't let third-party developers offer Claude.ai login or route requests through plan credentials, but its legal page says this doesn't "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription". A product that runs Claude Code must agree to the Commercial Terms, must not modify it or resell usage, and may not use the name in a product or feature name.
- **Claude: it still draws on the plan.** The separate credit pool announced for June 15 was paused. As of the Oct 7 update, `claude -p` signed in with a plan "still" draws from subscription limits. The monthly API credits (Max $100, Ultra $200, Team per seat; not Pro) only cover runs with an API key.
- **Claude: the biggest outside risk is `--bare`.** Anthropic says it "will become the default for `-p`", and bare mode never reads OAuth credentials. If that flips with no opt-out, subscription runs stop working. So: check for a plan sign-in at startup, fail with a clear line rather than silently, and raise it with Anthropic at the demo, since they're the audience.
- **Claude: a folder's hooks can be kept out without bare mode.** `--setting-sources user` reads neither the project's settings files nor its `.mcp.json`. `--settings '{"disableAllHooks":true}'` turns off hooks for the run. So for Claude, the question in step 3 is now about consent, not about protecting against code in the folder. For Codex, the spike checks that a repo's own `.codex` configuration runs nothing under `exec`.
- **ChatGPT: it isn't the same as Claude.** OpenAI offers an official sign-in, Sign in with ChatGPT, which open-source and locally hosted apps may use without approval. Running Codex is also allowed: `codex exec` reuses Codex's saved login by default. On app-server login OpenAI says "If you've built a local or open-source application using Codex app-server authentication, you can continue using it", recommends migrating to Sign in with ChatGPT, and adds that it "has never been permitted for commercial or hosted services". So if Redlines ever becomes a paid or hosted product, this route has to change. Its docs also call API keys "the recommended default for automation", but a plan sign-in is what people have, and what they'd want here.
- **Codex needs no Node.** `brew install --cask codex` or OpenAI's standalone installer both work.

**Wheels I looked at, and why these are the only ones we use:**

- **Agent Client Protocol (ACP)** is the real standard, used by Zed and JetBrains, with about 49 agents listed. It's right for the long tail, where agents speak it directly, and it's the answer to "generic enough for OpenClaw": a new agent becomes a line of configuration. But Claude and Codex only reach it through adapters. `claude-agent-acp` is built on the Agent SDK, the one place Anthropic's docs say third parties may not offer claude.ai login, and it adds a layer between us and the flags that keep a run safe. Anthropic's own docs name `claude -p` as the way to drive Claude from another language. So: direct for those two, ACP for everyone else.
- **oneharness** (one binary, uniform JSON, Claude Code, Codex and six others, version 0.28) is the closest thing to a ready-made wheel. It would put one person's project in the demo's critical path to save a few hundred lines, and its docs show how to turn MCP off but not how to hand it a server (I read only part of them). Worth another look if we end up with many direct providers.
- **harnesscli** is at 0.1.6, last published in February, from one owner. No.
- **The Claude Agent SDK and the Codex SDK** need Node or Python, and both drive the same binaries anyway.

| Provider | Starts | Notes |
| -------- | ------ | ----- |
| **Claude** | `claude -p` with `--output-format stream-json --verbose`, `--permission-mode dontAsk`, `--tools "Read,Grep,Glob"` (empty for This document), `--allowedTools` for the toolbox only, `--mcp-config` plus `--strict-mcp-config`, `--setting-sources user`, `--settings '{"disableAllHooks":true}'`, `--append-system-prompt`, in the folder | Sign-in state comes from `claude auth status`. This Mac has 2.1.201 and today's docs describe 2.1.302, so update it for the spike, and set a minimum version |
| **Codex** | `codex exec --json --sandbox read-only -C <folder>`, with the toolbox set through `-c mcp_servers…`, and `--ignore-user-config` and `--ignore-rules` if sign-in survives them | Sign-in state comes from `codex login status`. Not installed on the demo Mac yet. The spike confirms whether MCP tool calls run in `exec` without an approval prompt. If they don't, `codex app-server` (JSON-RPC over stdio, what OpenAI's own VS Code extension uses) is the next thing to try |

**Pitfalls for the builder:**

- **PATH:** apps started from Finder don't get the shell's PATH, so `claude` in `~/.local/bin` won't be found without looking in known places or asking a login shell. A `codex` installed with npm under nvm needs that PATH when it runs, too.
- **Credentials:** detection runs the agents' own status commands. Redlines never opens `~/.codex/auth.json` or the keychain.
- **Names:** the UI says "Claude", settings can say "runs Claude Code", and sign-in is a pointer to `claude auth login`.
- **Failures** are one line in the thread, never a dialog: "Claude isn't signed in. Run `claude auth login`." "Codex can't reach the network." The notification offers the log.
- **Stop** sends SIGINT first, because that ends Claude's turn cleanly, then kills the whole process group. Closing the window stops its runs.
- **A run belongs to its document.** Tools act on the live editor, so while a run is live in a window, anything that would replace its document (a sidebar click, File ▸ Open) opens a new window instead. Otherwise the next `str_replace` would land in the wrong file.
- **One run per thread at a time.** A second mention in that thread waits. Two agents named in one comment run one after the other.
- **A document with no file yet** runs at This document scope, with no folder.

## Modules

The rule: **the core carries what every host needs in order to show and edit a Redlines document. Everything else is a plugin, and a host picks its plugins.** Shared code never imports a host: nothing in `packages/` or `plugins/` touches `@tauri-apps` (a lint rule enforces it), and anything host-specific arrives through a `Host` capability.

| Piece | Where | Mac app | Embedded pane |
| ----- | ----- | ------- | ------------- |
| Format library | `@redlines/format` | Yes | Yes |
| Editing, preview, tracked changes, views, command registry | `@redlines/editor` (core) | Yes | Yes |
| Formatting commands and keymaps | `plugins/formatting` (new) | Yes | If the pane edits |
| Find and replace | `plugins/find` (new) | Yes | Optional |
| Syntax colors | `plugins/code` (new) | Yes | Yes (languages on demand) |
| Notes, cards, review bar | `plugins/review` | Yes | Yes |
| Themes and fonts | `plugins/themes` (tokens stay core) | Yes | Optional; a host may supply its own tokens |
| @ picker, status line, More, citation links | `plugins/agents` (new) | Yes | Yes |
| Agent providers | `plugins/agent-claude`, `plugins/agent-codex` (new); `plugins/agent-acp` later | Yes | No; the host answers `HostAgents` |
| Agent toolbox | `packages/agent-tools` (new) | Yes | The host's choice |
| Command logic | `packages/cli` (no Node in `commands.ts`; `node-io.ts` stays for development) | Inside the program below | No |
| The `redlines` program: Rust, QuickJS, the bundled logic | A small crate beside `src-tauri` | Yes | No |
| Menus, Preferences window, file sidebar, agent logs, updates, install, Dock icon, notifications | `apps/desktop` | Yes | No; a host has its own files and chrome |

**Commands are the seam.** A plugin registers a command with an id, a title, a default shortcut, a `run`, and an `isActive` for check marks. The core binds the keys. The Mac app draws its native menus from the registry (`apps/desktop/src/native-menu.ts` already builds them from TypeScript through Tauri's menu API, including check items), so a command works identically from the menu or the keyboard, and doesn't fire twice. An embedded pane has no menus; it gets the keys, and its host can show the commands however it likes.

**Keeping it honest:**

- **A size budget in CI.** Today, minified and gzipped: `@redlines/editor` with the format library is 239 KB; `@redlines/format` alone is 57 KB. A CI step bundles the smoke test's entry, a minimal embed of core plus `review` and `formatting`, and compares its gzipped size with a number committed in the repo. That number starts at the first measurement plus 15%, and raising it takes a deliberate commit. Fonts and language grammars stay out of it, loaded on demand.
- **An embed smoke test.** A bare test page mounts the core with a stub `Host` and no desktop code, and a test opens a document with marks in it. It isn't shipped. It fails the moment core code starts needing the app.
- **The format library stays engine-neutral.** It may use standard JavaScript plus `crypto.getRandomValues`, and nothing else. CI runs the built `redlines` through an end-to-end script (view, str-replace, comment, reply, accept, reject, and a reject that restores the exact bytes), so anything QuickJS can't run fails in CI rather than on someone's Mac.
